So, I was working on a programming assignment.

I had skipped the struct definition and was using definitions from space. I had also disabled the red squiggles, so I didn't notice that one of my so-called variables didn't exist until the function was already about 60 lines long.

Classic.

I started deleting things one by one, and all I could think was: I wish I could delete everything I need at once.

I always say that when you're an engineer, you should reduce problems wherever you can, because you have the power to solve them. So I did.

## What I built

**RangeEdit** is a VS Code extension that lets you scan, replace, and delete text within a selection or a specific range of lines. You tell it where to look, and it does the work across that whole range instead of making you edit line by line.

Under the hood, it's a C++ text-processing engine with a thin VS Code front end. The extension is the interface; the engine does the scanning and rewriting without touching the rest of the file.

It's now on the VS Code Marketplace.

## Okay, but why C++?

I know no one cares about peak memory and throughput numbers. Lowkey, I do. This project gave me a reason to care about them properly, and C++ made those tradeoffs explicit.

Here's the honest version:

- **Predictable memory ceiling.** The streaming CLI peaks at roughly **5.7 MiB** on a 1 GiB file. The Node version needed about **144 MiB**. This was the main reason.
- **Explicit streaming I/O.** I scan in **64 KiB** chunks, handle matches that cross chunk boundaries, write output atomically, and can add `mmap` later without rethinking the design.
- **Fine-grained cancellation and progress.** The engine checks for cancellation every **16 KiB** during literal scans, and between regex matches.

I wanted the engine to be explicit about where the time and memory go, instead of assuming the runtime would handle it.

## What I learned

The annoying part of a project is usually the part worth automating. I could have kept deleting lines manually, but I turned a small, recurring frustration into something I'll use again.

I also learned that shipping something small still counts. I didn't need a hundred features. I needed one thing that worked, and I needed to get it out.

## What's next

There's a lot I still want to improve, and I want to get better at documenting my projects, not just building them.

But the first version is out. It started with a 60-line function and a variable that didn't exist.
